# MIXHIVE Social Platform Scale Architecture

Prepared: 28 May 2026

## Decision

MIXHIVE should stay a modular monolith for the next production phase.

Do not split into microservices yet. The current product still needs fast iteration,
stable auth, reliable uploads, a stronger social graph, Redis recovery, and clear
observability before service boundaries are worth the operational cost.

Use this shape:

- Next.js/Vercel application as the product monolith.
- Supabase Postgres as the system of record.
- Supabase Realtime for first-pass live notifications and activity.
- Redis as cache, rate-limit, and ephemeral coordination layer once the provider
  endpoint is healthy.
- Supabase Storage/CDN for audio and images.
- Background workers for audio intelligence, AI agents, and ingest jobs.
- Extract services only when one domain has independent scale, runtime, or failure
  requirements.

## Why Not Microservices Yet

Microservices would add deployment coordination, tracing, service auth, schema
versioning, queue contracts, and local development overhead. MIXHIVE does not yet
have enough traffic or team capacity to justify that. The right move is a
service-ready monolith: clean modules, explicit interfaces, queues for slow jobs,
and observability from day one.

## Phase Goal

Make MIXHIVE production-ready as a social music platform:

- social feed and graph are stable under growth,
- media uploads are reliable and cacheable,
- auth/session/security are auditable,
- real-time notifications work without page refresh,
- AI/audio/background work cannot degrade core UX,
- production issues are observable quickly.

## Architecture Domains

### 1. Data Handling And Persistence

Current default:

- Keep Supabase Postgres as source of truth.
- Use relational tables for profiles, mixes, follows, likes, comments, playlists,
  notifications, AI suggestions, opportunities, and applications.
- Use `pgvector` for first-generation matching and recommendations.
- Use Redis for feed caches, trending caches, rate limits, and short-lived session
  coordination once the Redis Labs endpoint is repaired.

Near-term additions:

- Add indexes for high-read social queries:
  - `follows(following_id, created_at)` *(added)*
  - `likes(mix_id, user_id)` *(added)*
  - `comments(mix_id, created_at)`, `comments(parent_id, created_at)` *(added)*
  - `notifications(user_id, read, created_at)` *(added)*
  - `mixes(dj_id, created_at)`, `mixes(play_count, created_at)` *(added)*
  - `buzzes(author_id, created_at)`, `buzzes(parent_buzz_id, created_at)` *(added)*
  - `feed_events(target_id, created_at)`, `feed_events(target_id, type)` *(added)*
- Add feed materialization strategy:
  - MVP: query-time fan-out with indexed joins.
  - Next: cached home-feed pages in Redis.
  - Later: `feed_items` table generated by events.
- Defer NoSQL until clear write-volume pressure appears. Postgres JSONB can cover
  flexible payloads for AI suggestions, moderation signals, and analytics events.
- Defer external graph DB. Model the social graph in Postgres first; evaluate
  Neo4j only when graph traversals become product-critical and Postgres recursive
  queries/materialized views are not enough.
- Defer sharding. Plan for partitioning first:
  - partition high-volume analytics by month,
  - partition notifications/activity by time if needed,
  - archive old feed events.

### 3. Media Processing And Storage

Current state (as of Phase 4 completion):
- Supabase Storage for audio, images, avatars, banners, and generated assets.
- CDN-transformed asset URLs for public playback and image delivery.
- Upload validation at `/api/upload/validate` route (MIME type and size checking for audio, image, video).
- Media processing status tracked via `upload_status` column on mixes table: `uploaded` → `processing` → `ready` | `failed` (note: migration 041 changes 'error' to 'failed').
- Processing metadata includes: `processing_started_at`, `processed_at` (renamed from processing_completed_at via migration 041), `processing_errors`, `duration_seconds`, `audio_metadata`, `waveform_url`, `original_file_path`, `audio_quality`.
- Audio job queue system via `audio_jobs` table with job types: waveform, metadata, bpm_key_mood, tracklist.
- RLS policies restrict access to private buckets (`mixes-original`) to authenticated users only.
- Moderation signals table (`moderation_signals`) exists for append-only safety flags.
- Moderation status columns (`moderation_status`, `moderation_reason`) on content tables (mixes, comments, buzzes, profiles).
- Lua moderation agent registered and triggers on content insert/update to populate moderation signals and status fields.

Audio Worker Interface Contract (Phase 5):
- Job Payload (input to worker):
  ```typescript
  interface AudioJobPayload {
    mixId: string;          // UUID of the mix being processed
    jobType: 'waveform' | 'metadata' | 'bpm_key_mood' | 'tracklist';
    maxRetries?: number;    // Default: 3
  }
  ```
- Expected Result (output from worker):
  ```typescript
  interface AudioJobResult {
    mixId: string;
    success: boolean;
    waveformUrl?: string | null;      // URL to waveform JSON/PNG in supabase storage
    durationSeconds?: number;         // Audio duration in seconds
    bpm?: number | null;              // Beats per minute
    key?: string | null;              // Musical key (e.g., "C", "Am")
    mood?: string[];                  // Detected moods (e.g., ["happy", "energetic"])
    energy?: number;                  // 0-1 energy score
    danceability?: number;            // 0-1 danceability score
    error?: string;                   // Error message if success=false
    processingErrors?: unknown[];     // Array of processing errors
  }
  ```
- Backend Helper Functions (in `@/lib/database-queries.ts`):
  - `enqueue_audio_job(mixId, jobType, maxRetries)`: Enqueues a job and returns jobId.
  - `mark_audio_job_processing(jobId)`: Marks job as processing.
  - `mark_audio_job_complete(jobId, result)`: Marks job as complete and updates mix with results.
  - `mark_audio_job_failed(jobId, errorMessage, shouldRetry)`: Marks job as failed and updates mix with error.
- Database Tables:
  - `audio_jobs`: Stores queued/processing jobs with status, result, and error.
  - `mixes`: Updated by worker with `waveform_url`, `duration_seconds`, `audio_metadata`, `upload_status`, `processed_at`, `processing_errors`.
- Trigger: When a mix's `upload_status` transitions to 'processing', a waveform job is automatically enqueued (via trigger in migration 040).
- Service Role Authentication: Internal API routes (`/api/audio/process`) require service role token for worker-triggered job enqueuing.

- Ensure backend upload flow uses validation route and sets status accordingly.

Discovery Summary (Phase 5 Kickoff):
Media Schema & Storage:
- Core media table: `public.mixes` with columns: `audio_url` (required), `artwork_url`, `waveform_url`, `original_file_path`, `duration_seconds`, `audio_quality`
- Storage buckets: `mixes-original` (private, audio files), `mix-waveforms` (public, JSON waveforms), plus standard avatars/banners buckets
- Upload tracking: `upload_status` enum (`uploaded`|`processing`|`ready`|`error`), `processing_started_at/at`, `processing_errors` (JSONB), `duration_seconds`, `audio_metadata` (JSONB)
- Extensions: `uuid-ossp`, `pg_trgm`, `pgvector` (for embeddings)

Upload Flow:
- Client uploads directly to Supabase Storage (no proxy)
- Backend validation route: `/api/upload/validate` (POST) checks MIME type and size
- Allowed audio: MPEG, WAV, FLAC, OGG, AAC, MP4 (100MB max)
- Allowed image: JPEG, PNG, WEBP, AVIF (10MB max)
- Allowed video: MP4, WEBM (200MB max)
- After client upload, backend creates mix record with `upload_status = 'uploaded'`
- Audio processing pipeline: `audio_jobs` table enqueues jobs (waveform, metadata, bpm_key_mood, tracklist)
- Triggers automatically enqueue waveform job when status changes to 'processing'

Moderation & Content Fields:
- User-generated text locations:
  - Buzz posts: `buzzes.body` (text)
  - Mix descriptions: `mixes.description` (text)
  - Profile bios: `profiles.bio` (text)
  - Comments: `comments.body` (text)
- Moderation infrastructure:
  - `moderation_signals` table (migration 036): append-only log of moderation agent findings
  - Columns: `source_table`, `source_id`, `signal_type`, `severity`, `action_taken`, `flagged_by`, `payload` (JSONB)
  - Indexes: `(source_table, source_id)`, `(severity, created_at desc)`
  - RLS: enabled but no client policies (service-role only access)
  - Content-level columns (migration 039): `moderation_status` (enum: ''pending'', ''passed'', ''flagged'', ''hidden'', ''banned''), `moderation_reason` (text)
  - Tables with moderation columns: mixes, comments, buzzes, profiles
  - Lua moderation agent: registered (migration 035), triggered on content insert/update
  - Agent writes to `moderation_signals` and updates target row's `moderation_status`/`moderation_reason`

Worker/Background Job Handling:
- Existing audio job system: `audio_jobs` table (from migration 040)
- Job types: waveform, metadata, bpm_key_mood, tracklist
- Status tracking: pending → processing → complete/failed
- Retry mechanism: `max_retries`, `retry_count`
- Result storage: `result` JSONB column in audio_jobs
- Mix updates on job completion: waveform_url, duration_seconds, audio_metadata, upload_status='ready'
- Error handling: processing_errors JSONB array, upload_status='error'
- Helper functions: `enqueue_audio_job`, `mark_audio_job_processing`, `mark_audio_job_complete`, `mark_audio_job_failed`
- Service token authentication for internal routes (SERVICE_ROLE_TOKEN)
- Database RPC functions for job lifecycle management

  - text moderation before public feed insert where possible,

## Extraction Boundaries For Later

Only extract a separate service when the domain has a different runtime or scale
profile:

- Audio worker: extract first. It needs ffmpeg, Essentia/AudD, long jobs, and
  higher memory than web routes.
- Agent runner: extract second. It needs job queues, tool limits, retries, and
  model cost tracking.
- Realtime/chat: extract only when live chat or rooms become core.
- Feed service: extract only after feed generation becomes the bottleneck.
- Partner analytics: extract only when B2B dashboards need isolated SLAs.

### Supabase Realtime Configuration Checklist (Manual Step Required)

The following configuration must be completed in the Supabase Dashboard to enable real-time notifications:

☑️ **Enable Realtime for `notifications` table**
   - Navigate to Supabase Dashboard → Database → Replication
   - Find the `notifications` table in the list
   - Toggle the switch to **Enable** realtime updates
   - *Note: This is a one-time manual step that cannot be done via code*

☑️ **Verify Row Level Security (RLS) policy**
   - The existing policy `user_id = auth.uid()` already exists on the notifications table
   - No changes needed - this allows users to only receive their own notifications via realtime

☑️ **(Optional) Enable Realtime for supporting tables**
   - For immediate visibility of buzz_like events, consider enabling realtime on `buzz_likes` table
   - For repost events, consider enabling realtime on `feed_events` table (filtered by type='repost')
   - These are optional as the notifications table will catch all events via triggers
